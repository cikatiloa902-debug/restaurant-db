# Лабораторна робота № 5 Адміністрування бази даних ресторану

ЛР №5 використовує схему й навчальні дані ресторану з ЛР №4. Потрібні Docker
Desktop і Git Bash або WSL. Команди нижче запускайте у Git Bash з папки `lr5`.
Обидва сервери MySQL 8.0 працюють у власних томах Docker. Порти на комп'ютері
за замовчуванням 3307 та 3308. За потреби їх можна змінити у `.env` без зміни
внутрішнього порту MySQL 3306.

## Крок 1 Стенд

```bash
bash scripts/init_env.sh
docker compose up -d --build --wait
bash scripts/status.sh
```

Скрипт створює `.env` з випадковими лабораторними паролями, зберігаючи його, якщо він
уже є. Зробіть скриншот двох контейнерів зі статусами `healthy` і виводу
`@@server_id` (1 для primary, 2 для replica) та `@@gtid_mode` (ON для обох).
Схема й дані автоматично імпортуються лише в новий том primary.

## Крок 2 Облікові записи

```bash
bash scripts/roles.sh
```

Скрипт виконує `sql/01_users.sql` на primary, виводить `SHOW GRANTS` і демонструє
дозволені дії, три відмови 1142, блокування 3955 та розблокування. Перевірка
`UPDATE` виконується в транзакції з `ROLLBACK`. Перевірка DDL використовує
спеціальну порожню таблицю. Застосунок працює з роллю CRUD, аналітик має
`SELECT`. `backup_user` підключається тільки локально з контейнера primary.
Він читає дані та метадані для дампа і має привілеї для фіксації координат журналу.

## Крок 3 Журнали

```bash
bash scripts/logs.sh
```

Для звіту зафіксуйте `slow.log`, підсумок `mysqldumpslow`, `EXPLAIN`,
рядок про невдалий вхід з `general.log`, результати `SHOW BINARY LOGS`
і `SHOW MASTER STATUS`. Якщо утиліти `mysqldumpslow` немає в контейнері,
скрипт використає її з Git Bash або WSL, якщо вона там доступна. Для експорту
фрагмента на комп'ютер використайте команду:

```bash
docker compose exec -T primary cat /var/lib/mysql/slow.log > slow.log
mysqldumpslow -s t slow.log
```

Для запиту з пошуком за префіксом `name LIKE 'Борщ%'` можна запропонувати індекс
на `food(name)`. План для малої таблиці може віддати перевагу читанню таблиці.
Загальний журнал фіксує з'єднання та команди, тому його вмикають лише під час
налагодження. Повільний журнал допомагає знаходити запити для оптимізації.
Бінарний журнал зберігає події, потрібні для реплікації та PITR.

## Крок 4 Копія Перевірка Ротація

```bash
file=$(bash scripts/backup.sh)
ls -la backups/
bash scripts/verify_backup.sh "$file"
touch -d '10 days ago' backups/restaurant_db_test_old.sql.gz
bash scripts/backup.sh
ls -la backups/
```

`--single-transaction` дає узгоджений знімок таблиць InnoDB.
`--source-data=2` записує координати для PITR у коментарі дампа.
`verify_backup.sh` відновлює копію в окремій тимчасовій базі, порівнює кількість
рядків кожної таблиці, прибирає тимчасову базу та повертає помилку при розбіжності.
Команда ротації видаляє лише старі архіви цієї бази в `backups/`.

Приклад щоденного запуску о 02:15 через cron (у звіт підставте свій шлях):

```cron
15 2 * * * cd /path/to/lr5 && bash scripts/backup.sh >> backups/backup.log 2>&1
```

## Крок 5 Відновлення до аварії

```bash
bash scripts/pitr.sh
```

Скрипт створює тимчасову таблицю з посиланням на замовлення, робить повну копію,
додає два рядки, оновлює один і моделює випадкове видалення вмісту цієї тестової
таблиці. Далі знаходить початок транзакції видалення в binlog, завантажує копію в
окремий тимчасовий контейнер і застосовує журнал до знайденої межі. Зафіксуйте
координати й події, вивід кількості рядків до аварії, після аварії та після
відновлення, а також вивід збереженого INSERT і UPDATE. Скрипт перевіряє
рядки й прибирає тимчасовий контейнер після демонстрації. Якщо в образі сервера
немає `mysqlbinlog`, скрипт читає журнал утилітою mysqlbinlog з пакета mysql-server-core-8.0 в окремому контейнері Ubuntu.

## Крок 6 Реплікація GTID

Після кроків 2–5, на новій порожній replica:

```bash
bash scripts/replication.sh setup --reset-empty-replica
bash scripts/replication.sh verify
```

`setup` переносить узгоджений дамп разом із GTID, відтворює лабораторні облікові
записи без створення локальних GTID, потім підключає replica через
`SOURCE_AUTO_POSITION=1` і вмикає `super_read_only`. `setup` запускають один раз. Параметр `--reset-empty-replica` дозволяє видалити
локальні журнали та історію GTID лише на новій replica без користувацьких БД,
чужих GTID і каналу реплікації. Для порожньої історії GTID цей параметр зайвий.
Якщо початкове завантаження перервалося й replica вже містить дані, спершу перевірте
її стан та обсяг перенесених даних.

`verify` перевіряє INSERT на primary, появу користувача viewer, відмову прямого
запису від root і viewer на replica, відставання після STOP та наздоганяння після
START, а також поширення DELETE. Збережіть результати перевірок, стан обох
потоків, вивід `SHOW REPLICAS` і GTID з двох серверів. Поширення помилкового
видалення на обидва сервери показує, навіщо потрібна окрема резервна копія.

## Завершення роботи

```bash
docker compose stop
```

Для Moodle підготуйте посилання на GitHub і звіт з фактичними скриншотами кроків
1–6. ZIP можна додати як резервний варіант. `.env` і `backups/` зберігайте
локально.
