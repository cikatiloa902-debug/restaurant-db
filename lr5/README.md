Виконала Мазеїна Марина Олегівна, КІ-251. Дисципліна «Організація баз даних».

У роботі я використала схему й навчальні дані ресторану з попередніх лабораторних. На двох серверах MySQL 8.0.46 перевірила права користувачів, журнали, резервне копіювання, відновлення за бінарним журналом і реплікацію за GTID.

## 1. Запуск стенду

Команди виконуються з каталогу `lr5` у Git Bash або WSL. Для запуску потрібен Docker Desktop.

```bash
bash scripts/init_env.sh
docker compose up -d --build --wait
bash scripts/status.sh
```

`init_env.sh` створює локальний файл `.env` з лабораторними паролями. Схема та дані імпортуються в `primary` під час першого запуску з порожнім томом. На моєму стенді обидва контейнери отримали статус `healthy`.

| Сервер | Локальний порт | `server_id` | `gtid_mode` |
| --- | --- | --- | --- |
| `primary` | 3307 | 1 | ON |
| `replica` | 3308 | 2 | ON |

## 2. Облікові записи й права

```bash
bash scripts/roles.sh
```

У `sql/01_users.sql` визначено ролі застосунку й аналітика та службові облікові записи для копіювання й реплікації. Я перевірила дозволені операції та три очікувані відмови з кодом `1142`. Після трьох невдалих входів `app_user` отримав код `3955`. Після розблокування вхід знову пройшов.

## 3. Журнали MySQL

```bash
bash scripts/logs.sh
```

У `slow.log` зафіксовано два запити тривалістю 1,00 с і 0,80 с. План `EXPLAIN` для пошуку страви за префіксом показав повний перегляд таблиці `food`. Для цього запиту запропонувала індекс на `food(name)`. У `general.log` знайшла запис про невдалий вхід `app_user` і після перевірки вимкнула журнал. Стан бінарного журналу перевірила командами `SHOW BINARY LOGS` і `SHOW MASTER STATUS`.

Зведення `mysqldumpslow` отримала в допоміжному контейнері Ubuntu. Команди для повторення:

```bash
MSYS_NO_PATHCONV=1 docker compose exec -T primary cat /var/lib/mysql/slow.log > slow.log
docker run --rm -i ubuntu:22.04 sh -ec 'apt-get update -qq </dev/null
DEBIAN_FRONTEND=noninteractive apt-get install -y -qq --no-install-recommends mysql-client-core-8.0 perl </dev/null >/dev/null
cat >/tmp/slow.log
mysqldumpslow -s t /tmp/slow.log' < slow.log
```

## 4. Резервна копія та ротація

```bash
file=$(bash scripts/backup.sh)
bash scripts/verify_backup.sh "$file"
touch -d '10 days ago' backups/restaurant_db_test_old.sql.gz
bash scripts/backup.sh
ls -la backups/
```

Копію створено від імені `backup_user`. Після відновлення в тимчасову базу кількість рядків збіглася в усіх 11 таблицях, включно з тестовою таблицею для перевірки прав. Під час ротації видалено десятиденний тестовий файл. Файл `.env` і резервні копії зберігаються локально.

## 5. Відновлення на момент часу

```bash
bash scripts/pitr.sh
```

У тестовій таблиці було 3 рядки до видалення, 0 після видалення і 3 після відновлення. Для цього запуску застосувала події `binlog.000003` від позиції `61330` до початку транзакції видалення на позиції `62047`. Дві вставки й одне оновлення, виконані після створення копії, збереглися.

## 6. Реплікація за GTID

Початкове налаштування виконується один раз на порожній лабораторній репліці. Параметр `--reset-empty-replica` дозволяє очистити її локальні журнали та початкові GTID перед імпортом.

```bash
bash scripts/replication.sh setup --reset-empty-replica
bash scripts/replication.sh verify
```

Перевірила, що вставка з `primary` з’являється на `replica`, а `viewer` може її прочитати. Прямий запис від `root` і `viewer` повернув код `1290`. Після `START REPLICA` репліка отримала запис, доданий під час паузи. Видалення на `primary` поширилося на `replica`. Наприкінці GTID збіглися, обидва потоки працювали, затримка становила 0 секунд.

Для зупинки стенду використовується `docker compose stop`.
